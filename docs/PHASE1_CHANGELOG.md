# 采策第一阶段改造说明

## 本次范围

本次只改造前端输入交互和 Render 数据选项接口。没有修改 Dify `.ifpkg`、工作流节点 ID、采购优化算法、五个功能的结果版式或图表。

## 已完成

1. 删除前端右上角状态胶囊（包括“Dify 已配置”文案）；保留 `/api/status` 检查和运行按钮的服务可用性控制。
2. 五个功能统一使用可搜索、可展开的采购需求 Combobox。下拉选项只显示：
   - 采购企业名称
   - 产品名称
   - 净采购需求件数
3. 断供模拟增加可搜索、可展开的供应商 Combobox，只显示企业名称，并且只展示当前采购请求报价数据中出现的候选供应商。
4. 搜索支持关键词包含匹配和字符顺序模糊匹配。完整且唯一的企业/产品名称可在提交时解析；模糊片段显示候选结果，用户需要点击或键盘确认，不会自动选中第一个模糊结果。
5. 断供模拟、缺口恢复引用断供情景、报价交期沿用原来的请求关联和场景锁定逻辑。
6. 前端可见的输入标签、提示、用户提交记录不再展示采购请求编号或供应商 ID。决策报告下载文件名也改为企业名和产品名。
7. Render 后端新增只读 `GET /api/options`：
   - 不带 `request_id`：返回全部可选采购需求。
   - 带 `request_id`：额外返回该请求下的候选供应商。
8. 后端进程内缓存 Excel 解析结果 5 分钟，并在 `/api/analyze` 调用 Dify 前校验采购请求和断供供应商，防止伪造或过期的前端选项。
9. 新增轻量 XLSX 读取模块，使用 Node.js 内置 `zlib` 解析当前工作簿所需的工作表；没有增加 npm 依赖。

## 数据口径

选项接口读取与当前 Dify 工作流相同的两个 GitHub Excel 地址：

- 采购请求工作表：`缺货采购请求`
- 供应商报价工作表：`供应商模拟报价`

候选供应商口径与当前 Dify 风险评估和断供合法性检查保持一致：按采购请求筛选报价后，对报价中的非空供应企业 ID 去重。当前 Dify 的断供合法性节点只检查供应商是否存在于风险评估结果的 `suppliers` 集合中，因此本次没有额外添加“自动采购资格通过”过滤，以免前端列表与 Dify 校验口径不一致。

内部 `request_id`、`supplier_id` 仍然保留在前端隐藏字段和后端请求载荷中，仅用于调用 Dify 和验证业务关联，不在选择器中显示。

- 采购需求读取：30 条。
- 供应商报价读取：600 条。
- 30 个采购请求均完成候选供应商映射检查，共核对 150 个请求—供应商关系。
- `REQ-001` 返回 5 家候选供应商：潮州三环（集团）、广州鹏辉能源、华灿光电、江苏长电科技、深圳蓝普视讯。

- 合法候选供应商断供演示：HTTP 200，成功生成情景令牌。
- 使用情景令牌继续报价交期测算：HTTP 200。
- 跨来源 Origin 请求：HTTP 403。
- Node.js 全部源码语法检查：通过。
- `npm ci --ignore-scripts --no-audit --no-fund`：通过，无新增依赖。

当前执行环境的 Chromium 浏览器访问本地站点被运行环境策略拦截，因此没有完成真实浏览器点击自动化测试。前端脚本语法已通过检查；部署后仍应按下方步骤进行一次实际页面验证。

## Render 部署

1. 先备份当前 Render GitHub 仓库或保留当前部署 commit。
2. 解压本次源码 ZIP，将文件覆盖到 Render 所连接仓库的根目录。
3. 提交并推送，等待 Render 自动部署。
4. 不需要更换 `DIFY_API_KEY`，也不需要修改 Dify 工作流。
5. 数据源默认使用与当前 Dify 工作流一致的 GitHub 地址；如更换文件地址，可选配置 `PROCUREMENT_REQUESTS_XLSX_URL` 和 `PROCUREMENT_QUOTES_XLSX_URL`。缓存最长约 5 分钟刷新。
